# Batched aux models (recognition, 106- and 68-point landmarks) in the tracking pre-pass (2026-10-05)

**CODE REMOVED (the owner chose removal after this report).** The implementation, its 23 tests and the harness were deleted;
they are recoverable from commit `f11c8c2` (`app/roop/aux_batch.py`, the `_apply_aux` / `aux_batch_scope` seam in
`face_util.py`, `app/tests/ab_aux_batch.py`, `app/tests/test_aux_batch.py`). This document and the raw JSON stay as the
record of the negative result - do not re-attempt without a pre-pass that keeps >= 4 faces in flight. Tense below is as written
when the code existed; `ROOP_AUX_BATCH*` flags no longer exist.

Brief: run w600k recognition, `landmark_2d_106` and `landmark_3d_68` batched across the faces of the frames in flight in
`procmgr_tracking._precompute_tracks`, with GPU affine crops using insightface's transform math instead of per-face
`model.get` + `cv2.warpAffine`; batch axis relaxed like `FaceSwapInsightFace._relax_batch_dim`, TRT profile 1..16;
`_consume` still in strict frame order. Acceptance: embeddings cosine >= 0.999, landmarks within 0.3 px of the CPU path on
500 faces, identical tracks and source assignments; report `track_detect` ms and pre-pass fps.

**Result: implemented, wired, tested - and NOT enabled. Every configuration is slower or neutral (GPU crops -23% FP16 / -31%
FP32 pre-pass fps; CPU crops -3% FP16 / -18% FP32), because the pre-pass never has enough faces in flight to fill a batch. `ROOP_AUX_BATCH=1` opts in. The 0.3 px landmark criterion is also unreachable
against the existing path, for a reason that is a finding in itself (section 3).**

Code: `app/roop/aux_batch.py` (engine), `face_util._apply_aux` / `aux_batch_scope` (the seam, one helper behind the four
per-face aux loops), `procmgr_tracking._precompute_tracks` (scope around the scan). Harness: `app/tests/ab_aux_batch.py`.
Unit tests: `app/tests/test_aux_batch.py` (23, no GPU needed). RTX 4070, `config.yaml` live (scrfd, TensorRT mixed,
detmask pool 2, 10 threads), `ROOP_PROFILE=1`.

## 1. Speed - the pre-pass gets slower

`_precompute_tracks` over d4 frames 0..600 (step 1, `collect_obs=True`), 5 tracks in every arm. Arm order A A B C C B A / A D E E D A
(the first A is warm-up and the null). `track_detect` is the stage the aux models run inside (ms per call, thread time).

| arm | what | runs: pre-pass fps | `track_detect` ms |
|---|---|---|---|
| **A** | per-face aux models (today) | 62.9, 66.6, 64.6 / 60.9, 64.9 | 29.3, 28.8, 29.7 / 30.3, 29.7 |
| B | batched, FP16, GPU crops | 49.8, 50.3 | 39.1, 38.6 |
| C | batched, FP32, GPU crops | 44.1, 43.8 | 44.2, 44.7 |
| D | batched, FP16, CPU (`cv2.warpAffine`) crops | 62.0, 58.7 | 31.2, 33.0 |
| E | batched, FP32, CPU crops | 51.9, 51.8 | 37.5, 37.5 |

A vs A is identical (null: tracks, boxes and assignments equal). Engine statistics, read off the engine's own counters:
**579 batches for 785 faces: 1.36 faces per batch, exactly 1.00 frames per batch** - no cross-frame coalescing happened at
all, in any arm. With 2 detector workers at most two frames can ask at once, and the aux models are ~3 ms of a ~29 ms detect,
so the calls almost never overlap.

Why each step costs what it costs:
- Batching has nothing to amortise at 1.4 faces/batch. In isolation the three models cost 0.60 + 0.81 + 1.02 = 2.4 ms/face at
  B=1 and 0.21 + 0.30 + 0.39 = 0.9 ms/face at B=4 (FP16, 96 large faces) - but B=4 never occurs here. Arm D (batching only,
  CPU crops) is the neutral-to-slightly-worse floor: 62.0 / 58.7 against 60.9 / 64.9.
- The GPU crop (arm B vs D) costs ~2.7 ms more per batch than the CPU crop it replaces: `cv2.warpAffine` of a 112/192 px crop is
  ~0.1 ms, so the upload + int64 gather + sync is a loss, not a saving, and it competes with the detector on the same GPU.
- FP32 (C, E) adds ~0.4 ms/face on the 68-point model and ~0.6 on recognition (TRT FP32, B=4: 0.71 / 0.95 ms vs 0.30 / 0.39).

The ceiling is also small: the aux models are ~11% of `track_detect` thread time on d4 (3 x 2.2 ms x 1,271 faces = 8.4 s of
73.6 s in `baseline_2026-10-04.md`), and a stage's thread-time share is not a speedup budget (AGENTS.md). Even ideal batching
(B=2.7, ~1.5 ms/face saved) is ~6% of a detect, inside what this machine cannot resolve.

**What would change this:** a pre-pass that keeps >= 4 faces in flight at once - deferring the aux step across several frames
- which `_detect_faces` cannot do as written: `_upright_remeasure` compares the new embedding against the old one and
`refine_landmarks` reads the 68 points inside the same call, so the aux results are needed before the frame's detection returns.

## 2. Tracks and source assignments

Same 5 tracks, same frame ranges and observation counts, **source assignments identical in every arm** (0 frames differ);
track mean-embedding cosine >= 0.99993 (FP16 0.99995, FP32 0.99993). **Not identical per observation:** the largest bbox
difference between A and a batched arm is **15.2 px** on some observation (0.0 px A vs A). Cause NOT investigated; the likely
route is `_upright_remeasure` / the partial-miss rescue choosing a different candidate when an embedding norm moves by FP16
noise (`nc > no + 2.0`), but that is a guess. Measured on d4 only; d1, d6 and Love were not run through the pre-pass A/B.

## 3. Accuracy - 0.3 px against the existing path cannot be met, and why

503 real faces (d4, d1, Love; face size median 220 px, p90 387, max 476), detector `aux=False` so every arm gets the same
bbox/kps. Landmark errors are in FRAME pixels (crop-space error / (192 / (1.5 x face size)) - a 400 px face turns 0.1 crop px
into 0.5 px). Reference "FP32 truth" = the same per-face code on a fresh CUDA FP32 session.

| vs FP32 truth | embedding min cos | lm106 max / p99 px | lm106 faces > 0.3 | lm68 max / p99 px | lm68 faces > 0.3 |
|---|---:|---|---:|---|---:|
| existing per-face, TRT FP16 | 0.999939 | 0.30 / 0.19 | 0 | **9.5 / 5.9** | **485** |
| batched FP16 | 0.999895 | 0.75 / 0.60 | 148 | 7.3 / 5.8 | 497 |
| batched FP32 | 0.999995 | **0.13 / 0.04** | 0 | 1.9 / 0.75 | 40 |

Against the existing path directly: batched FP16 lm106 max 0.81 px (134 faces > 0.3), lm68 max 3.9 px; batched FP32 lm106
max 0.43 (2 faces > 0.3), lm68 max 9.5 (dominated by the existing path's own error).

- **Embeddings pass in every configuration** (min cosine 0.99981 against the existing path, 0.99989 FP16 / 0.99999 FP32 against truth).
- **The existing 68-point model is not a usable reference at 0.3 px.** Under TensorRT FP16 it sits a median 1.25 px (max 9.5)
  from FP32 truth on these faces; a 1-grey-level change of input moves it ~1 crop px. No other FP16 engine - batched or not,
  with any crop - can land within 0.3 px of it; the batched engine is no farther from truth than the existing path (median
  1.249 vs 1.256 px on 96 faces), so it is the same quality, not a worse one. Two different TRT engines (profile 1..16 vs the
  live implicit profile) already differ by 0.6 px median on lm68 with the SAME input crop.
- The crop is not the cause. `affine_crops` reproduces `cv2.warpAffine` **bit for bit** (zero differing samples over 5.9 M; the
  crop blobs are `np.array_equal` to cv2's on 96 real faces): OpenCV's 8-bit warp is fixed point (inverse matrix rounded to
  1/1024 px, sample position 1/32 px, four 15-bit weights, the (0,0) weight saturating to 32767 then corrected to a sum of
  32768) and that arithmetic is emulated on the device. A `grid_sample` crop is 3 grey levels off and was measurably worse.
- **FP32 is the configuration that meets the spirit of the criterion** (lm106 0.13 px, embeddings 0.999995, lm68 p99 0.75 /
  40 of 503 faces over 0.3, the tail on small faces) and it would make the pre-pass landmarks MORE accurate than today's - but
  at -31% pre-pass fps, so it was not adopted. `ROOP_AUX_BATCH_FP16=0` selects it.
- Batch composition does not change results: a call per frame and 4 threads coalescing give **bit-identical** outputs.

`kps` after `refine_landmarks` moved by up to 4.7 px between the per-face and batched FP16 paths on the same frames (the
68-point noise above, propagated through `_refine_kps_from_68`); this is in the opt-in path only.

## 5. Things found on the way

- **A reference can silently be the thing it checks.** With `ROOP_PROFILE=1`, `baseline_probe.wrap_counter` puts a `get`
  wrapper on each live model as an INSTANCE attribute, bound to that model; `copy.copy(model)` copies the wrapper, so my
  first "FP32 truth" ran the live TRT session and read identical to it (0.000 px everywhere). Caught because "live vs truth"
  matched the null control to the last digit. Truth is now a fresh object of the class with its own session.
- The three aux ONNX files already have a dynamic input batch axis but a FIXED output batch (`[1, 512]`, `[1, 212]`,
  `[1, 3309]`); `_relax_batch_dim` fixes the outputs (and any Reshape constant); batch-8 and batch-1 outputs are bit-identical
  on the relaxed graphs. The live sessions carry an empty TRT profile (`trt_profile_*_shapes: ''`), so they cannot batch;
  the engine builds its own three sessions (extra VRAM not isolated; 117 s cold TRT build, ~1.3 s warm).
- `trt_fp16_enable` for the three sessions in a stock `FaceAnalysis` is on under `trt_precision: mixed`; the 68-point model is
  the FP16-fragile one.
