# Multi-scale detector: reuse the single pass, stop spawning executors (2026-10-04)

Change: `face_detector.MultiScaleFaceDetector.detect` (commit `292faa0`). Reference code: `c4bfff9`.
RTX 4070, `config.yaml` live, 10 threads.

**Scope first.** The pyramid is reached only by the `retinaface` / `retinaface_r50` engines. The user's config is
`detector_engine: scrfd`, and the baseline renders have no `pyramid.*` counter at all, so **this change does not touch a
render on the current config**. Everything below was measured on `retinaface_r50`, the only pyramid-capable detector
model present locally; `retinaface_10g.onnx` is not downloaded, so 10g was not run on real weights (the logic is
engine-independent and covered by unit tests).

## What changed

1. **Reuse.** When the adaptive single pass triggers the pyramid, its result is the pyramid's scale-1.0 level (same
   padded image, same `det_size`/`det_thresh`), so it fills that slot and only the other scales run:
   **4 -> 3 detector inferences per triggered frame.** The slot is kept (the DIoU merge is order-sensitive on ties).
   No reuse when there was no single pass (estimated-height trigger, configured scales) or the pyramid has no 1.0 level.
2. **Scale passes.** *"Generate the scaled images from the already-padded frame once"* was already how the code worked:
   `generate_scale_pyramid(padded_frame, ...)` builds every level once from the single padded frame, and level 1.0 is that
   frame object itself, so there was nothing to change there. What changed is where the passes run: in the calling thread
   when it is a pool worker, else on one persistent module-level executor (no `ThreadPoolExecutor` per call).
   "Pool worker" is read off the FaceAnalysis pool rather than thread names or the outer pools' creation sites:
   every pyramid call comes from `_detect_faces_raw`, which holds a pooled analyser lease while the detector runs, and
   `lease_face_analyser` marks the thread for exactly that long (cleared on the error path too).
3. `should_trigger_pyramid` and all thresholds untouched (pinned by a test).

Detector inferences (counted at `detect_fn`), same frames:

| source | frames | triggered | old | new | per frame old -> new |
|---|---:|---:|---:|---:|---|
| **d6 4K** | 488 | 488 | 1952 | 1464 | **4.00 -> 3.00** |
| Love 1100..1700 | 600 | 8 | 624 | 616 | 1.04 -> 1.03 |

| synthetic close-ups | 80 | 71 | 293 | 222 | 3.66 -> 2.78 |
| **all** | 1468 | 569 | 3175 | 2606 | 2.16 -> 1.78 |

Per triggered frame: **4.0 -> 3.0** exactly. In a real render (below) d6 makes 5.5 `detect()` calls per frame (per 100
frames: 100 full detects + 100 upright re-measures in the pre-pass, then 202 ROI crops and 148 detector-only re-detects in
the main pass, 114 of those in discarded stabilizer warm-up), every one of them triggers the pyramid,
so detector inferences per frame go **22.0 -> 16.5** (-25%). On natural 720p footage the pyramid almost never triggers
(10 of 900 frames), so the saving there is ~1%.

with `detector_engine` forced to `retinaface_r50` (harness flag; `config.yaml` untouched), old / new / new / old, each with

## Speed

Function level, 40 triggered d6 frames x2, ABBA (old, new, new-with-reuse-only, new-with-reuse-only, new, old), calls/s:

| callers | old | new | new, reuse only (pool-worker shortcut off) |
|---|---:|---:|---:|
| 1 plain thread (pool idle) | 12.65 | 14.15 (**+11.8%**) | 14.01 (+10.8%) — same code path as "new" here, so the 1% gap is the noise |
| 2 pool-worker threads (render-like) | 26.29 | 28.69 (**+9.1%**) | 29.43 (+11.9%) |

So the gain is from **item 1** (+10.8% to +11.9%), less than the -25% in inferences because the host work on a 4K frame
(padding, resizes, NMS, rescale) is untouched. **The sequential-in-pool-worker rule is neutral** (28.7 vs 29.4, inside the
1-8% scatter between repeats of one arm); it is implemented as specified and the executor path is one line away.
Persistent executor vs per-call executor could not be separated from reuse: both are in "reuse only".

Render level speed is **not measurable**: pre-pass 25.1 s (old), 23.2 s and 27.3 s (new), then 41.1 s for the last (old)
arm, which also ran its frame loop at 0.26 fps against 0.43 in the first three. GPU utilisation, RAM, temperatures and
clocks looked the same in all four; the late-arm slowdown (also seen on Love in the previous brief) is not isolated.

## A side finding: on r50 the pyramid is not redundant

Because r50 resizes every input straight to 640x640, I expected the 0.5x / 0.75x / 1.0x levels to be near-copies and the
merge to equal the plain single pass. It does not. On d6 the plain single pass returns **2 boxes on 235 frames, 3 on 206
and 4 on 47** (the clip has two people), while the pyramid merge returns **2 on 446 frames and 3 on 42** — fewer boxes than
the single pass on 213 of 488 frames, more on none. Across the other 81 triggered frames the merge has fewer boxes on 8
and the same on 73. I did not check which boxes are which, so "the merge removes duplicates" is the likely reading, not a
measured one. (An earlier note of mine said the merge returned exactly 2 boxes on all 488 frames; that was wrong.)
