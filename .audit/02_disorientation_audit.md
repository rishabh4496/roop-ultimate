# Bug #1 — Face disorientation audit

**Scope:** Static call-path audit of the current source for faces that rotate, flip, skew, jump, or attach the wrong geometry in selected frames. The pipeline map was read first. No source files were changed. This report is an audit of reachable code and documented behavior, not a frame-level reproduction.

**Relevant repository rules applied:** `AGENTS.md` Part 1 (read current recode/validation evidence; audit actual call sites instead of inferring from names; classify unverified behavior honestly; inspect logs when investigating). Part 2 concerns launcher scripts and does not apply because this task changes no launcher. The latest crash record reviewed, `logs/crash_459c97b8514d_20261115_224828.json`, is a queue test that intentionally raises `kaboom`; it contains no face geometry or render evidence.

## Findings at a glance

| Failure mode | Finding | Confidence from source audit |
|---|---|---|
| Landmark alignment | The production renderer fits an unweighted five-point similarity transform and immediately warps with it. It does not gate semantic point order, geometric residual, fitted scale, or transform validity. Finite but badly regressed points can therefore create a very wrong crop matrix. | Confirmed structural hazard |
| Detector roll | There are both per-frame and track roll paths. They use different angle thresholds and, when 68-point landmarks exist, different landmark axes. A roll estimate can therefore cross a hard turn boundary or disagree between remeasurement and track resolution. | Confirmed inconsistency; frame symptom is conditional |
| Temporal geometry | A temporal prepass smooths tracked landmarks, but fills gaps by interpolating coordinates. The fallback/no-prepass path distributes nonadjacent frames across workers, causing the contiguous-frame landmark smoother to decline. | Confirmed mode-dependent hazard |
| Multi-face identity | Most temporal matching is track-based and global, not list-index-based. `swap_mode="first"` is explicitly leftmost, however, and rotated-face re-detection matches on IoU only. These can select another face when faces cross or overlap. | Confirmed selection hazards in those cases |
| FP16/TRT | The 106- and 68-point landmark models are explicitly FP32 in the precision overrides. The detector family can use mixed precision, so finite but less accurate detector keypoints remain a possible upstream cause. No evidence ties a specific observed disorientation to FP16. | Not established as a root cause |
| Async frame metadata | Frame indices travel with work into each worker; the current per-face matrix is local and thread-local. The writer relies on round-robin queue order and drops the explicit index from output payloads, but current workers emit one output/fallback per input. No current cross-frame `M`/bbox attachment was found. | No current defect found; fragile ordering contract |

## Current render path

For batch video, detections are enriched and sanitized in `app/roop/face_util.py:1887-1995`. With `temporal_detection` enabled, `app/roop/procmgr_tracking.py` builds per-frame faces, fills eligible short gaps, smooths per track, and resolves roll. `ProcessMgr` consumes the face list keyed by the same `frame_idx` at `app/roop/ProcessMgr.py:3943-3959`, selects a face/source, optionally re-detects after a cardinal turn, then calls `canonicalize_face_alignment` at `app/roop/ProcessMgr.py:5662-5737`. That function gets `kps` and calls `estimate_norm`; the resulting `M` is used for `cv2.warpAffine` and is stored on the current face / thread at `app/roop/ProcessMgr.py:5736-5772`.

The active swap alignment is therefore the five-point path. The 68- and 106-point sets help with roll, masks, and other processing; they are not the landmarks used by `canonicalize_face_alignment` to fit the swap crop matrix.

## 1. Affine alignment and landmark degeneracy

### Production fit

`app/roop/face_util.py:2694-2703` defines the five-point ArcFace destination in the order left eye, right eye, nose, left mouth, right mouth. `estimate_norm` at `app/roop/face_util.py:3477-3512` asserts only that the input has shape `(5, 2)`, chooses `skimage.transform.SimilarityTransform` (`use_affine = False`), and calls `tform.estimate(...)`. For non-square pixels it scales input x coordinates by SAR before the fit and adjusts the first matrix column afterward (`:3487-3509`). Neither branch checks the return value of `estimate`, validates the fitted matrix, checks the landmark-to-template residual, or bounds the crop scale. `align_crop` immediately passes the matrix to `cv2.warpAffine` (`:3517-3542`). The actual swap crop repeats that direct fit/warp through `canonicalize_face_alignment` at `app/roop/face_analyser.py:695-735`, particularly `:710-730`.

This is a similarity fit, not a free six-parameter affine fit or a call to `cv2.estimateAffinePartial2D`. Constraining it to rotation + uniform scale + translation prevents ordinary affine shear and, in the normal `SimilarityTransform` solver, excludes a reflected solution. That is a useful safeguard, but it does not make the result safe when the five semantic points are wrong. An erroneous point can rotate/translate the whole crop; a collapsed eye span can demand a very large scale to map the observed eyes to the fixed canonical eye distance; yaw and occlusion make the projected face depart from the frontal template even when all values are finite. Because all five points are fitted without robust weights, one wrong eye or mouth point can pull the full fit.

The repository documents a concrete detector failure class in `app/roop/face_util.py:1533-1562`: an inverted head may still score about 0.98 while its five points are geometrically crushed. The comments report interocular distance shrinking from 177 to 136 px and eye-to-mouth distance from 202 to 134 px, and note the same points can mis-scale/off-center both recognition and swap crops. This is evidence that confidence and finiteness do not establish usable geometry.

### Validation gap

`sanitize_faces` at `app/roop/face_sanity.py:73-141` catches malformed/nonfinite arrays, invalid boxes, and zero/invalid embeddings. Its keypoint gate is shape/finite only (`:122-127`). `face_analyser._valid_landmarks_5` likewise checks only `(5,2)` and finite values (`app/roop/face_analyser.py:1626-1633`). Neither gate checks eye separation, eye-mouth distance, expected face scale, point ordering, or fit residual. Thus finite collapsed, permuted, or semantically mislocalized points can reach the crop fit.

The stricter checks shown in the pipeline map are not on this active path. `LandmarkGeometrySanity.validate_landmarks` and `validate_affine_matrix` are defined at `app/roop/geometric_alignment.py:60-125`; the affine check tests singular values, similarity condition, scale, and positive determinant. Its visible production use is inside `PoseAwareAlignmentSolver.solve` at `:557-562`. `canonicalize_face_alignment` does not call that solver; it directly invokes `estimate_norm` (`app/roop/face_analyser.py:721`). The profile/weighted solver and `TemporalGeometryStabilizer` in `geometric_alignment.py` are likewise not called by the active renderer found in this audit. The corresponding Stage 2 description in `.audit/01_pipeline_map.md:221-271` should therefore be read as listing available implementation, not proof that those checks guard the render crop.

`app/roop/adaptive_detector.py:97-184` also defines geometry validation, but the batch render path calls `get_all_faces` (`ProcessMgr.py:3998`; tracking prepass call sites in `procmgr_tracking.py`), not the separate adaptive-detection route. That validator is not a substitute for checking the matrix at the active crop boundary.

### Ordering, reflection, and degeneracy conclusions

The code assumes the detector's index contract is stable: indices 0–4 map to the same anatomical features as the destination template. There is no active-render check that verifies this ordering or the residual against it. A detector can hallucinate an otherwise finite five-point set on a profile, blur, occlusion, or inverted face; if semantic labels or positions jump, the fit may produce a sudden rotation/scale jump even though a mirrored affine is not permitted. A check based only on x-coordinate order would be wrong for rolled faces; validation must be pose-aware.

**Fix specification:** Before warping, validate the five points and resulting matrix: finite values; noncollapsed eye and eye-to-mouth baselines; face-relative scale bounds; positive determinant; acceptable similarity singular-value ratio; and normalized Procrustes residual against the canonical template. Use detector confidence/visibility and pose to down-weight occluded points or choose a documented pose-aware fit. Treat failed/degenerate fits as “do not swap this face” or re-detect/recover the same track, rather than passing an unchecked matrix to the model. Keep the guard in the function the renderer actually calls. Emit per-frame diagnostic values (track, IOD/bbox ratio, fitted scale, determinant, residual, rejection reason) so a bad crop can be tied to input geometry.

## 2. Detector orientation and auto-rotation

There are three distinct behaviors; the pipeline map’s description can make them sound like one universal multi-angle pass:

1. `face_rotation_action` derives a frame-level action from the 68-point axis, five-point eye-to-mouth axis, then a bbox fallback (`app/roop/face_util.py:2542-2656`). The direct action threshold is `FACE_ROLL_LOWER = 54.5°`, with the 180° branch above 135° (`:2498-2499`, `:2614-2619`).
2. In a temporal track, `orientation.action_for_roll` uses a 45° lower boundary and 135° upper boundary (`app/roop/orientation.py:45-46`, `:156-210`). It has hysteresis after an action is established, but a new track accepts the first proposed action immediately (`:327-356`). The roll predictor also trusts an estimate within 40° and coasts on a rejected estimate for up to 45 observations (`:48-58`, `:245-302`). A wrong first observation can therefore seed the wrong action; later outliers can hold that state while coasting.
3. Detection-time rotated rescue is conditional, not an every-frame angle sweep. `_detect_faces` tries cardinal rotations when the original pass finds no faces (`app/roop/face_util.py:1902-1957`), and a separate partial-miss rescue tries turns when fewer than `expected_count` faces were found (`:1966-1995`). The rescue turns are 180°, clockwise, and anticlockwise (`:1359-1375`, `:1973-1984`). Normal detection with a found face does not independently try all four orientations. `ProcessMgr.process_face` can still rotate/re-detect the selected face when its roll action requests it (`app/roop/ProcessMgr.py:5662-5711`).

The ~40–55° boundary is a real discontinuity zone. The fallback action begins at 54.5°, whereas a track action begins at 45°. A direct/fallback path can chatter as noisy roll moves around 54.5°; a new temporal track can issue a quarter-turn at 45° on its first measurement. Established track actions have deadbands and multi-observation transition logic, but that protection does not validate the initial estimate (`orientation.py:171-210`, `:327-356`). Also, the track path’s 45° convention is not identical to the `face_util` fallback.

There is a further estimator mismatch: track orientation prefers the 3D-68 nasion-to-chin line (`app/roop/orientation.py:78-134`), while `face_util.face_down_axis` uses the 3D-68 eye-to-mouth line when available (`app/roop/face_util.py:2502-2539`, `:2569-2594`). The source comments report strong roll accuracy for those axes in different measured conditions, but a track-resolved action bypasses the later “did the turn improve uprightness?” test in `ProcessMgr.py:5690-5701`. A disagreement between estimators can therefore become an applied turn instead of being vetoed by that test. The 106-point axis is also documented as unreliable in the inverted band (`face_util.py:2515-2522`); it is not a safe independent vote there.

The upright remeasurement path is a mitigation, but its correspondence is not fully constrained. `_upright_remeasure` re-detects on the rotated frame and chooses the nearest unrotated candidate center within half a face width (`app/roop/face_util.py:1573-1645`). It does not reserve a chosen candidate for one original face. The render-time `_match_rotated_face` uses only bbox IoU (`app/roop/ProcessMgr.py:5491-5511`) and `_unrotate_face_to_parent` then copies that candidate’s keypoints, landmarks, and embeddings into the original target (`:5514-5560`). With overlapping/contacting faces, geometry from a neighbor can be committed to the target. This is a conditional identity/geometry mismatch risk, not proof it occurs on every rotated face.

**Fix specification:** Unify the roll estimator and thresholds between prepass, remeasurement, and render fallback. Require a short confidence/continuity check before the first track action; retain the existing hysteresis for subsequent transitions. Have the turn gate compare track-predicted roll, the candidate’s post-turn roll, and identity/track evidence. Match rotated detections one-to-one using unrotated bbox plus landmark residual, embedding, and predicted track position; do not let multiple originals claim the same candidate. Log the raw estimate, selected axis, previous action, proposed action, and post-turn delta for each changed action.

## 3. Temporal jitter, tracking, and face indexing

### Smoothing and gap fill

Temporal detection is enabled in the checked live config (`app/config.yaml:8`, `:215`, `:229-230`). The prepass is not unsmoothed: it builds track timelines, fills eligible gaps, smooths kps/dense landmarks/bbox, then resolves roll after smoothing (`app/roop/procmgr_tracking.py:3223-3239`, `:3290-3434`). Short gaps are filled by coordinate interpolation (`_interp_face`, called at `:3227-3234`). If the endpoints are detections whose point ordering or pose estimate is inconsistent, linear interpolation can create a geometrically invalid midpoint and then snap back to the closing detection. The visible gap-fill assignment does not run the canonical alignment residual/scale checks described above. This is a plausible source of a one-frame crop jump around occlusion, blur, or a bad endpoint.

The usual prepass smoothing is track-local. But in the no-prepass/failure path, video workers receive round-robin frame indices: `read_frames_thread` places frame `n` on queue `n % num_threads` (`app/roop/ProcessMgr.py:1743-1776`), so each worker sees every Nth frame rather than adjacent frames. The inline landmark smoother explicitly declines unless its prior state is frame `frame_index - 1` (`ProcessMgr.py:3798-3829`). `procmgr_batch` also turns off temporal mode when prepass construction fails (`app/roop/procmgr_batch.py:1030-1037`). Thus no-prepass and prepass-fallback renders have less temporal stabilization of `kps` and `M` than the normal temporal path, despite the per-worker stabilizer being configured. That mode-dependent loss can expose detector jitter as frame-to-frame crop movement.

The zero-phase track smoother includes 68-point landmarks (`procmgr_tracking.py:3364-3372`, `:3394-3400`), while the causal/adaptive branch shown at `:3401-3415` updates 5-point and 106-point landmarks but not 68-point landmarks. Since `orientation.roll_from_face` reads 68-point landmarks when present, its roll signal can differ from the smoothed 5/106-point geometry on that branch. This is an orientation consistency risk rather than a general absence of smoothing.

### Face ordering and identity association

`get_all_faces` returns detections sorted by x coordinate (`app/roop/face_util.py:2086-2101`), and `get_first_face` explicitly returns the leftmost face (`:1998-2004`). The `swap_mode == "first"` path uses the leftmost face on each temporal frame (`app/roop/ProcessMgr.py:3961-3972`). If two people cross or their boxes move past one another, “first” can change identity even when detections are otherwise correct. That is a deterministic consequence of the selection rule.

Other temporal selection is more robust than raw detector list ordering: it matches tracks globally using appearance, motion, IoU, and scale, then rejects a nearly tied association instead of forcing it (`app/roop/temporal_tracker.py:455-516`). This reduces confidence-driven list swaps. However, a detection miss, low-quality embedding, or ambiguous crossing can still break track continuity and lead to a new/unmatched track; the per-frame fallback then has less reliable identity continuity. The audit did not find evidence that fluctuating detector confidence directly permutes source/target assignments in the normal tracked path.

**Fix specification:** For temporal geometry, interpolate a pose/roll-aware representation only when endpoint geometry and identity are consistent; refuse interpolation if the fitted-template residual or landmark semantic checks fail. Preserve track-indexed smoothing in fallback mode, or explicitly bypass swaps when continuity cannot be maintained. For `first` mode, either document leftmost as intended semantics or lock the initial face to a track and use track identity through crossings. For rotated re-detections and upright remeasurement, require one-to-one candidate assignment with a track/prediction gate.

## 4. FP16 / TensorRT numerical instability

The active numerical risk is upstream keypoint accuracy, not an FP16 affine grid. `app/roop/precision_policy.py:458` explicitly forces `2d106det` and `1k3d68` to FP32 (along with other overrides); the policy table at `:143-145` classifies face detection and recognition/landmark families separately. The face detector family may still be eligible for mixed precision according to the selected model/provider policy, so a finite but shifted five-point regression remains possible. The active geometry sanitizer catches nonfinite kps and embeddings (`face_sanity.py:122-140`), but it cannot catch a finite, anatomically wrong regression.

The main crop matrix is a NumPy/skimage similarity fit followed by OpenCV `warpAffine` (`face_analyser.py:721-730`), so there is no FP16 affine-grid calculation in that path. The optional torch-frame warp in `app/roop/processors/frame/onnx_swappers.py:50-86` explicitly promotes the matrix and sampling grid math to float64/float32 before `grid_sample`. That path is not the main `ProcessMgr` canonical crop shown above.

There are normalization sites without epsilon/finite guards in swapper latent preparation: converter output and post-emap normalization in `app/roop/processors/frame/onnx_swappers.py:322-340`, and converted latent normalization in `app/roop/processors/FaceSwapInsightFace.py:1111-1122`. A zero converter/emap result can produce a nonfinite identity latent. These sites do not compute `M` or the target crop orientation; they are an indirect identity/selection risk at most, not a demonstrated geometric cause.

**Fix specification:** Keep FP32 precision for the landmark regressors as policy requires. For every actual detector provider used in a render, compare per-frame kps and fitted `M` against FP32 on the same orientation/occlusion fixtures, recording scale, residual, determinant, and angle deltas; do not infer stability from successful inference or finite tensors. Add epsilon and finite checks after latent conversion as a separate robustness fix, and fail the identity operation clearly if invalid.

## 5. Async queue and frame metadata desynchronization

The frame reader enqueues `(num_frame, frame)` together (`app/roop/ProcessMgr.py:1743-1776`). Each worker unpacks that exact index and calls `process_frame(..., frame_idx=frame_idx)` (`:1911-1950`). Temporal faces are looked up by that index (`:3947-3955`). Alignment `M` is then stored on the current face and in thread-local state (`:5736-5772`), not a global mutable affine slot. The batcher likewise keeps each submitted request/result paired by request (`app/roop/swap_batcher.py:107-125`, `:147-173`). No code path found attaches an `M` or bbox from another frame solely because a batched swap completed out of order.

There is an implicit ordering contract at the writer: workers enqueue `(True, resimg)` without the frame index (`ProcessMgr.py:1972-1979`), and the writer consumes queues in round-robin order, incrementing the output index (`:2021-2029`). Current input dispatch is also round-robin and each worker submits one output or a fallback for every dequeued frame, so the two sequences align. This would become unsafe if a future worker path skipped/doubled an output or changed dispatch order, but it is not evidence of a present metadata desync. It affects output ordering, not the local `M` used during the current worker’s crop.

**Fix specification:** As a defense-in-depth change, retain `frame_idx` in the processed payload and have the writer reorder by explicit index. Add a bounded pending map and duplicate/missing-index diagnostics. This is preventative; the current audit found no reproduced or source-evident `M`/bbox cross-frame attachment.

## Recommended order of investigation/fixes

1. **Guard the active crop fit** in `canonicalize_face_alignment`/`estimate_norm`; log and reject bad input geometry before `warpAffine`. This is the shortest path from degenerate landmarks to a rotated, enlarged, or skewed crop.
2. **Make orientation decisions consistent and continuous** across the track resolver, remeasurement, and fallback; strengthen initial track validation and one-to-one rotated-face matching.
3. **Protect temporal gaps and fallback mode** against invalid interpolated geometry and unsmoothed round-robin detections; make `first` face semantics track-stable if identity continuity is expected.
4. **Verify actual provider precision on the repro clip** and compare detector landmarks/matrices with FP32. The current source does not establish FP16 as the primary cause.
5. **Make writer ordering explicit** by carrying frame indices through output queues. The current pipeline’s per-face matrix remains worker-local, so this is hardening rather than a confirmed fix for Bug #1.

## Audit limitation

No source edits were made; the audit findings come from static call-path inspection. For the requested commit, `app/env/Scripts/python.exe -m pytest` was attempted (7,965 selected, 4 deselected), but the run was stopped at 96% after `face_engine/tests/test_cuda_streams.py` made no progress for several minutes while an FFmpeg child remained open waiting for pipeline input. Failures had already appeared in several unrelated app test groups, so this was not a passing full-suite run. The disorientation-relevant groups that completed, including orientation, affine/roll geometry, temporal tracking, and rotated-face matching, passed.

Without a failing clip/frame and a per-frame trace of raw landmarks, track ID, selected roll axis/action, fitted `M`, and provider, the conditional hazards above cannot be ranked against each other for the reported footage. In particular, this audit found no evidence that async metadata desync or FP16 NaN/Inf is the observed root; it did find a direct, unchecked finite-but-degenerate-landmark path into the crop transform.
